# 0002 — typescript: initial generation

- **Date**: 2026-09-21
- **Language**: `typescript`
- **Module**: `system` — full initial generation covering all three modules

- **Spec version**: started from commit `90b9a409a6e019e74ba2f79bff63966cd763c162`

- **Acceptance version**: all four `blueprint/features/*.feature` files
  (`url-creation.feature` — including the "Length limit counts Unicode code

  `redirects.feature`, `expiration.feature`, `metadata.feature`) and every

- **Trigger**: initial generation — no prior `typescript/` implementation

- **Agent/author**: generated by a single coding agent working directly from

- **Result**: every scenario across all four `.feature` files passes, as
  Vitest tests in `typescript/tests/`, named after their scenario titles.
  Every applicable `blueprint/GUARANTEES.md` entry holds, verified via
  fast-check property tests in `typescript/tests/guarantees.test.ts`,
  including a dedicated concurrency property test that fires N concurrent
  `GET /{code}` requests via `Promise.all` for random N and asserts
  `click_count` increases by exactly N. One gap was found during
  generation: `specs/url-creation.md`'s "at most 2048 characters" rule was
  silent on how to count a character requiring a UTF-16 surrogate pair
  (e.g. many emoji) — JavaScript's native string length counts UTF-16 code
  units, which would silently diverge from Python's code-point-based
  `len()` for such inputs. Closed by adding an explicit "characters means
  Unicode code points" rule to `blueprint/specs/url-creation.md`, a new
  scenario to `blueprint/specs/url-creation.md` and
  `blueprint/features/url-creation.feature`
  ("Length limit counts Unicode code points, not UTF-16 code units"), then
  implementing (`typescript/src/validation.ts` counts code points via the
  spread operator) and testing it. Two other Node-specific behaviors were
  identified and handled without requiring a spec change, since the specs
  already dictated the desired behavior and only the implementation
  technique was in question: (1) the WHATWG `URL` parser silently strips
  ASCII tab/newline characters from its input, so control-character
  rejection is implemented as an explicit pre-check on the raw string
  rather than relying on `URL` to reject it; (2) JavaScript's `Date`
  constructor interprets a timezone-less date-time string as local time,
  not UTC, so naive `expires_at` values are normalized (a trailing `Z` is
  appended when no timezone designator is present) before parsing, to
  satisfy `shared-conventions.md`'s "naive timestamps are interpreted as
  UTC" rule. Implementation choice (noted for context only, not binding on
  future regenerations): Node.js with Fastify, Zod for request-shape
  validation and the `ShortUrl`/`ValidationError` schemas, an in-memory
  single-process store, Vitest + fast-check for tests. The redirect
  module's `click_count` increment path is written to be fully synchronous
  (no `await` between reading and mutating a record), which is what makes
  the concurrency guarantee hold under Node's single-threaded event loop —
  see the comment in `typescript/src/modules/redirect.ts`. No known open
  gaps as of this entry.
